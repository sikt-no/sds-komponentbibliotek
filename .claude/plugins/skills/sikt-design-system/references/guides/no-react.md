# Using the Sikt Design System without React

The SDS packages ship both React components **and** the compiled CSS that styles
them. Consumers who are not on React — vanilla HTML, static sites, Vue, Svelte,
server-rendered templates — can still adopt the visual system by:

1. Installing the packages they need and importing the CSS.
2. Writing HTML that matches the markup the React components produce.
3. Implementing any interactive behavior themselves.

This guide walks through the pattern and points to the pre-rendered HTML
snippets that make it concrete.

## What this skill provides for non-React users

For every component package, `references/html/<slug>.md` contains the exact
HTML produced by the React component for every Storybook story. Copy-paste one
of those snippets, and — with the corresponding CSS imported — it will render
identically to the React version.

The snippets are generated by rendering each story with
`react-dom/server.renderToStaticMarkup`, so they are the real, verified output
of the components. Re-run `npm run skill:sync` after any component change to
refresh them.

**What is provided:**

- Suggested HTML structure per component variant.
- Correct CSS class names (BEM: `sds-<component>`, `sds-<component>--variant`,
  `sds-<component>__part`).
- Correct ARIA attributes for the static markup.

**What is _not_ provided (consumer responsibility):**

- Event handling (`onClick`, form submission, keyboard shortcuts).
- Dynamic state (open/closed dialogs, active tabs, expanded details).
- Focus management (dialog focus trap, popover restore-focus, etc.).
- Popover/dropdown positioning.
- ARIA state that changes over time (`aria-expanded`, `aria-selected`,
  `aria-current`, `aria-controls` wiring across DOM nodes).

The snippets show a single point-in-time render — usually the "open" or
"default" state — and it is up to the consumer to reproduce transitions.

## Setup

1. Install the packages you need, plus `@sikt/sds-core`:

   ```sh
   npm i -s @sikt/sds-core @sikt/sds-button @sikt/sds-input
   ```

2. Import the CSS in a global stylesheet (never per-component). `@sikt/sds-core`
   provides the reset, tokens, and base typography — always import it first.

   ```css
   @import "@sikt/sds-core/dist/index.css";
   @import "@sikt/sds-button/dist/index.css";
   @import "@sikt/sds-input/dist/index.css";
   ```

3. Some packages depend on other SDS packages internally (e.g. `@sikt/sds-button`
   renders `@sikt/sds-notification` inside a button with a badge). Import the
   CSS for every transitive SDS dependency too — the list is in each package's
   entry under `references/components/<slug>.md`.

## Icons and SVGs

Snippets contain two kinds of SVG placeholders:

- `<!-- icon: XxxIcon -->` — an icon. The name matches an export in
  `references/icons.md`; the SVG source for each icon lives in
  `packages/icons/build/`.
- `<!-- svg -->` — any other SVG (typically the Sikt logo inside Header/Footer,
  or a story-local illustration).

The skill is deliberately unopinionated about **how** you render the SVG —
inline `<svg>`, sprite/`<use>` reference, `<img src="…svg">`, an icon-component
library, etc. The wrapping element in the snippet already carries the
sizing/color classes; the inner SVG only needs to fill it (e.g. `width="100%"
height="100%" fill="currentColor"`).

## IDs and label wiring

Some snippets contain placeholder IDs like `REPLACE_ME_0` (sometimes as part of
a composite ID such as `REPLACE_ME_0-heading` or `panel-REPLACE_ME_0-0`). These
come from React's `useId` and have been rewritten to make them easy to
find-and-replace. Substitute your own stable IDs and update every attribute
that references them (`aria-labelledby`, `aria-controls`, `for`, etc.) so
labels and inputs stay linked.

## Component index

The pre-rendered HTML lives under `references/html/`. One file per package,
mirroring the component reference structure:

- Component API and CSS class inventory: `references/components/<slug>.md`
- Pre-rendered HTML per story: `references/html/<slug>.md`
- Package version, exports, transitive CSS deps: same `references/components/<slug>.md`
- Design tokens (colors, spacing, typography): `references/tokens/*`
- Icon catalogue: `references/icons.md`
- Auto-generated overview with links per package: `references/index.md`

When picking HTML for a specific component, open `references/html/<slug>.md` and
pick the story name that matches the variant you want (e.g. `IconLeft`,
`WithNotification`, `Small`, `Disabled`).

## Regenerating the snippets

The HTML files are auto-generated. From the repo root:

```sh
node --experimental-strip-types --no-warnings=ExperimentalWarning \
  .claude/plugins/skills/sikt-design-system/scripts/generate-html.ts \
  <slug> [<slug>…]
```

Or, if wired into `npm run skill:sync`, that command regenerates everything —
component references, tokens, icons, and HTML snippets — in one go.

## Complex components: what the consumer owns

A few components need meaningful state/behavior on the consumer side. The
snippets show the target HTML; the runtime logic is yours to write.

- **Dialog** — snippets render the `<dialog>` element with its contents. You
  need to call `.showModal()` / `.close()` on the native element, toggle
  `document.body.style.overflow` for modal dialogs, and update
  `aria-expanded` on the trigger button. `closedby` is a native attribute of
  `<dialog>` in modern browsers.
- **Popover** — snippets show the popover panel HTML. Positioning relative to a
  trigger is not modeled; use CSS Anchor Positioning, Floating UI, or the
  browser's Popover API.
- **Tabs** — snippets show one panel visible at a time. Toggle
  `aria-selected` / `tabindex` on the tab buttons and `hidden` on the panels in
  response to click and arrow-key navigation.
- **Combobox / Select** — the visible input plus a listbox variant is rendered.
  Filtering, keyboard navigation, and `aria-activedescendant` are consumer
  responsibility.
- **Details** — uses the native `<details>` element, so open/close works
  without JavaScript. Just include the `open` attribute for the initial state.
- **ToggleSwitch / Checkbox / Radio** — native form controls; state is managed
  by the form.
- **Header** — the mobile menu open/close, submenu expansion, and skip-link
  focus are consumer responsibility.
- **InputDatepicker** — this is a heavy composite component (calendar popover,
  keyboard navigation, locale-aware formatting). If you need it without React,
  consider either shipping a small React island for this one component, or
  substituting a native `<input type="date">` with the SDS input classes for
  visual parity.
